# Lume Cloud protocol — v1

This is the wire contract between the Lume Cloud server (`server/`, a
Cloudflare Worker) and every client: Apple (`LumeCloudKit/`, Swift) and Android
(LumeAndroid, Kotlin). It is normative. If an implementation disagrees with
this file, the implementation is wrong. Changes within v1 are **additive only**.

The server is **zero-knowledge**. It stores opaque encrypted records and a
per-account change feed. It never sees keys, plaintext, logical keys or catalog
ids.

## 1. Conventions

- **Base URL:**
  - Official: `https://cloud.getlume.org`
  - Staging: `https://cloud-staging.getlume.org`
  - Every path below is prefixed with `/v1` unless noted.
- **JSON:** UTF-8 with camelCase keys. Unknown response keys MUST be ignored
  by clients, and unknown request keys MUST be ignored by the server.
- **Binary values** (keys, ciphertext, HPKE material) are **base64url without
  padding** (RFC 4648 §5).
- **Times** are integer **epoch milliseconds, UTC**.
- **UUIDs** inside payloads and logical keys are **uppercase** with dashes
  (Swift `uuidString`).
- **Errors** are a non-2xx status with the body `{"error": "<code>", "message": "<optional human text>"}`.

| Status | `error` | Meaning |
|---|---|---|
| 400 | `bad_request` | Malformed JSON, missing fields, or a bad base64url value |
| 401 | `bad_auth` | Missing or wrong credentials |
| 401 | `device_revoked` | This device was revoked. Stop syncing and show "removed from Lume Cloud". |
| 403 | `signup_closed` | `SIGNUP=invite`, and the invite code is missing or wrong |
| 404 | `account_deleted` | The account doesn't exist (deleted, purged, or never existed). The client switches to local-only and keeps its local data. |
| 404 | `not_found` | Unknown route, or the pairing code expired or doesn't exist |
| 409 | `account_exists` | `POST /accounts`: an account with this `accountId` already exists. Sign in to it instead (§4.8). |
| 409 | `pairing_already_sealed` | Someone else already sealed this pairing |
| 400 | `bad_request` | Also returned when `X-Lume-Device` is missing on a route that requires it |
| 410 | `resync_required` | `since` is older than the tombstone horizon. Do a full resync (§6.3). |
| 413 | `record_too_large` | A record's ciphertext is larger than 65,536 bytes (decoded), or the push body exceeds the limits |
| 429 | `rate_limited` | Honour the `Retry-After` header (seconds) |
| 507 | `quota_exceeded` | The account would exceed 10 MiB of ciphertext, 100,000 live records, 100,000 pending tombstones, or 100 devices |
| 503 | `unavailable` | Transient server-side allocation failure (pairing code, or a server-picked account id). Retry later. |

## 2. Keys & crypto

All algorithms are available in CryptoKit (Apple) and in JCA/Tink (Android).
`spec/vectors/crypto.json` pins every step with known-answer tests.

### 2.1 Root key and derived keys

- `rootKey`: 32 random bytes, generated by the device that creates the account.
- Derived values, from HKDF-SHA256 (RFC 5869) with salt = empty (zero-length)
  and IKM = `rootKey`:

  | Value | `info` (UTF-8) | Length `L` | Use |
  |---|---|---|---|
  | `encKey` | `lume-cloud/v1/enc` | 32 bytes | Record envelopes (§2.4) |
  | `idKey` | `lume-cloud/v1/id` | 32 bytes | Record ids (§2.3) |
  | `authKey` | `lume-cloud/v1/auth` | 32 bytes | Auth (§2.2) |
  | `accountId` | `lume-cloud/v1/account` | 16 bytes | `accountId = base64url(HKDF(…))`, 22 characters |

- The `accountId` is derived, not assigned: every device holding the root key
  (including one that has only the recovery key, §4.8) computes the same id.
  It isn't secret; it travels in every `Authorization` header.

### 2.2 Auth

- `authVerifier = base64url(SHA-256(authKey))`, sent once at account creation
  and stored by the server.
- Every authenticated request carries:
  - `Authorization: Bearer <accountId>.<base64url(authKey)>`
  - `X-Lume-Device: <deviceId>`. This is required on every authenticated
    route except `POST /accounts` and `POST /devices` (the latter registers the
    id in its body).
- The server checks `base64url(SHA-256(authKey)) == authVerifier`, comparing in
  constant time.
- It returns `device_revoked` when the device id is marked revoked. An unknown
  (unregistered) device id is accepted, so a device that crashed before
  registering can still recover.

### 2.3 Record id

`rid = base64url(HMAC-SHA256(idKey, UTF8(logicalKey)))`, which is 43
characters. It's deterministic: every device holding the account key computes
the same `rid` for the same logical key.

### 2.4 Record envelope

```
envelope = 0x01 || nonce(12 random bytes) || AES-256-GCM-ciphertext || tag(16 bytes)
key      = encKey
AAD      = UTF8(rid)
wire     = base64url(envelope)
```

- Use a fresh random nonce on every write.
- A client that sees an unknown version byte skips the record. It keeps the
  record and never overwrites or deletes it.

### 2.5 Payload (the plaintext inside the envelope)

UTF-8 JSON in **RFC 8785 canonical form (JCS)**:
- keys sorted by UTF-16 code units at every level;
- ECMAScript number formatting (`1`, `0.00001`, `1e-7`, `1e+21`);
- `JSON.stringify` string escaping;
- no insignificant whitespace.

`spec/vectors/` pins it.

```json
{"data":{...},"key":"content/<PROFILE-UUID>/<contentId>","type":"content","v":1}
```

| Field | Meaning |
|---|---|
| `v` | Payload schema version (1) |
| `type` | The collection (§3) |
| `key` | The logical key. It's carried here because `rid` can't be reversed. |
| `data` | The collection's fields (§3) |

**Unknown fields inside `data` MUST be preserved verbatim** and written back on
the next push. Unknown `type` values MUST be kept and never deleted.

## 3. Collections and payload fields

Field names match the Apple mirror models. Optional fields may be absent or
`null`. Dates are epoch milliseconds.

| `type` | Logical key | `data` fields |
|---|---|---|
| `playlist` | `playlist/<UUID>` | `id` (UUID), `name`, `serverURL`, `username`, `password`, `macAddress`, `sourceTypeRaw`, `epgURL?`, `syncEnabled` (bool), `hiddenTabsRaw`, `updatedAt` |
| `content` | `content/<profileUUID>/<contentId>` | `contentId`, `kindRaw` (`movie`\|`series`\|`episode`\|`live`\|`category`), `profileID` (UUID), `watchProgress` (seconds, double), `isWatched`, `lastWatchedDate?`, `isFavorite`, `addedToWatchlistDate?`, `favoriteOrder?` (int), `isHidden`, `customOrder?` (int), `recommendationVoteRaw` (int: -1, 0 or 1), `updatedAt` |
| `profile` | `profile/<UUID>` | `id`, `name`, `symbolName`, `colorRaw`, `createdAt`, `sortOrder` (int), `isChild` (bool), `updatedAt` |
| `epgSource` | `epgSource/<UUID>` | `id`, `name`, `url`, `isEnabled`, `updatedAt` |
| `parentalPin` | `parentalPin` | `pinHash` (lowercase hex SHA-256 of `"lume.parental.v1" + pin`), `updatedAt` |
| `categoryRestriction` | `categoryRestriction/<categoryID>` | `categoryID`, `isRestricted`, `updatedAt` |
| `sportsFollow` | `sportsFollow/<profileUUID>/<key>` | `key`, `kindRaw`, `profileID`, `sortOrder` (int), `updatedAt` |
| `recordingServer` | `recordingServer/<UUID>` | `id`, `kindRaw`, `name`, `baseURL`, `serverID?`, `deviceID?`, `token`, `isEnabled`, `updatedAt` |
| `liveTVPrefs` | `liveTVPrefs` | `showsFavorites`, `showsRecentlyWatched`, `updatedAt` |

In content keys, `<profileUUID>` is the literal `none` when `profileID` is
nil (legacy records).

## 4. Endpoints

### 4.1 Accounts

**`POST /v1/accounts`** (unauthenticated, rate-limited per IP)

```json
→ {"authVerifier":"<b64url>","accountId":"<22-char derived id, §2.1>","invite":"<optional, only when SIGNUP=invite>"}
← 201 {"accountId":"<the accountId sent>","createdAt":1760000000000}
```

- `accountId` MUST match `^[A-Za-z0-9_-]{22}$`; anything else (wrong length,
  padding, `+`/`/`, a non-string, `null`) is `400 bad_request`.
- If an account with that id already exists, the response is
  `409 account_exists` and the existing account is left untouched. A client
  that gets it signs in to that account instead (§4.8).
- The per-IP signup limits (§5) apply to every attempt, including a `409`.
- **Deprecated:** a request without `accountId` still creates an account
  under a random, server-assigned id (16 random bytes, base64url). A
  recovery key can't restore such an account. Clients MUST send `accountId`;
  the fallback exists only for clients written before the id was derived.

**`DELETE /v1/accounts/me`** → `204`. Afterwards every call returns
`404 account_deleted`.

**`GET /v1/accounts/me`**

```json
← 200 {"accountId":"…","createdAt":…,"usedBytes":1234,"recordCount":56,"nextSeq":789}
```

### 4.2 Devices

**`POST /v1/devices`** registers or updates this device. It's idempotent by
`id`.

```json
→ {"id":"<UUID>","name":"Philipp's iPhone","platform":"ios|tvos|macos|visionos|android|androidtv"}
```

The platform list is open: the server accepts any `[a-z][a-z0-9]{0,31}` token,
and clients must display unknown platforms generically.

```json
← 200 {"id":…,"name":…,"platform":…,"createdAt":…,"lastSeen":…,"revoked":false}
```

**`GET /v1/devices`**

```json
← 200 {"devices":[ {…device…} ]}
```

**`DELETE /v1/devices/{id}`** → `204`. It marks the device revoked, and that
device then gets `401 device_revoked`.

A revoked device id can never be registered again: `POST /devices` with that id
also returns `401 device_revoked`. A device that is re-added through pairing
uses a fresh UUID.

Revocation is soft: a revoked device still knows the root key. True removal
needs key rotation, which is v2.

### 4.3 Change feed

**`GET /v1/changes?since=<seq>&limit=<1…1000, default 500>`**

```json
← 200 {
  "records":[{"rid":"…","version":3,"seq":41,"deleted":false,"ciphertext":"<b64url>","updatedAt":…}],
  "nextSeq":42,
  "hasMore":false
}
```

- Records with `seq > since` come back in ascending `seq` order. A record
  appears once, at its latest `seq`.
- For a tombstone, `deleted:true` and `ciphertext:null`.
- `nextSeq` is the value to send as `since` next time: the highest `seq`
  returned, or the unchanged `since` when nothing came back.
- `since=0` returns the full live set **without tombstones**. Once anything
  has been compacted, the first `since=0` page always extends past
  `compactedSeq` (even beyond `limit`), so paging a full snapshot can never
  land in the `410` range. That page is bounded by the account quota.
- If `0 < since < compactedSeq`, the response is `410 resync_required`.

### 4.4 Push

**`POST /v1/push`**: at most 500 records and 4 MiB per request.

```json
→ {"records":[{"rid":"…","baseVersion":3,"deleted":false,"ciphertext":"<b64url>"}]}
← 200 {"results":[
     {"rid":"…","status":"ok","version":4,"seq":43},
     {"rid":"…","status":"conflict","current":{…record as in /changes…}}
   ],"nextSeq":44}
```

- `baseVersion` is the version the client last saw. Use `0` for a record it
  has never seen.
- A write applies only when `baseVersion` equals the stored version. A record
  that doesn't exist has version 0; a tombstone keeps its version.
- An unknown `status` value in a result means the record wasn't applied.
  Clients keep it dirty and retry on a later pass.
- On success, `version = old + 1` and the record gets a fresh `seq`.
- A delete sends `deleted:true, ciphertext:null` and leaves a tombstone.
- The records in a request are evaluated independently, and conflicts don't
  fail the rest. Quota and size checks are evaluated for the whole request
  first: one over-limit record → `413`/`507` for the whole request, and
  nothing is applied.
- `nextSeq` in the push response (and in `/accounts/me`) is the **next seq the
  server will assign**. It's informational only and **MUST NOT be used as a
  `/changes` cursor**. Clients advance their cursor exclusively from
  `/changes` responses (`nextSeq` there = the highest seq returned). Records a
  client pushed itself come back through `/changes` on its next pull; that's
  expected, and they are no-ops when the payload equals `lastSyncedPayload`.
- A conflict on a record that never existed returns
  `current = {rid, version:0, seq:0, deleted:true, ciphertext:null, updatedAt:0}`.
- After a successful push that changed anything, the server sends a poke on
  every open WebSocket of the account (§4.6).

### 4.5 Pairing (moving the account key to a new device)

The cipher suite is HPKE (RFC 9180) base mode:
**DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / AES-256-GCM**, with
`info = UTF8("lume-cloud/v1/pairing")` and `aad = UTF8(code)`.

CryptoKit has no predefined constant for this suite, so build it explicitly:
`HPKE.Ciphersuite(kem: .Curve25519_HKDF_SHA256, kdf: .HKDF_SHA256, aead: .AES_GCM_256)`.

The `code` used as AAD is exactly the 6 ASCII digits the server returned. Clients
strip whitespace and separators from user input before using it; the server
only ever issues and accepts `^[0-9]{6}$`.

The flow:

1. **New device** (unauthenticated, rate-limited per IP) sends
   **`POST /v1/pairings`**:

   ```json
   → {"publicKey":"<b64url raw 32-byte X25519>","deviceName":"Living Room","platform":"tvos"}
   ← 201 {"code":"483920","pollToken":"<b64url 32 random bytes>","expiresAt":…}
   ```

   The code is 6 decimal digits and is valid for 10 minutes.

2. **Joined device** (authenticated) sends **`GET /v1/pairings/{code}`**:

   ```json
   ← 200 {"publicKey":"…","deviceName":"Living Room","platform":"tvos","expiresAt":…}
   ```

   It's rate-limited per account at 10 per minute. An expired or unknown code
   returns `404 not_found`.

3. The joined device shows "Add **Living Room** (tvOS)?". After the user
   confirms, it seals the payload
   `{"accountId":"…","rootKey":"<b64url>","serverURL":"https://cloud.getlume.org"}`
   (keys sorted) to `publicKey`, and sends
   **`POST /v1/pairings/{code}/seal`** (authenticated):

   ```json
   → {"enc":"<b64url encapsulated key>","ciphertext":"<b64url>"}
   ← 204
   ```

   It's first-writer-wins: a second seal returns `409 pairing_already_sealed`.

4. **New device** polls **`GET /v1/pairings/{code}/result?pollToken=…`**,
   unauthenticated, every 2 seconds:

   ```json
   ← 200 {"status":"pending"}
   ← 200 {"status":"sealed","enc":"…","ciphertext":"…"}
   ```

   It opens the payload with its private key. The server deletes the pairing
   after the sealed result has been fetched once, or when it expires.

5. The new device derives its keys and sends `POST /v1/devices`. It's now
   joined.

The grant still carries `accountId` for compatibility. It MUST equal the id
derived from `rootKey` (§2.1); a receiver may derive it instead of reading it.

### 4.6 Realtime

**`GET /v1/socket`** is a WebSocket upgrade, authenticated with the same
headers.

- **Server → client:** `{"type":"seq","seq":44}` whenever the account's feed
  advances. `seq` is the highest seq assigned so far, so a client pulls only
  when it's greater than its stored cursor.
- **Client → server:** the text `ping` every 30 s. The server answers `pong`
  automatically without waking the server object.
- Clients MUST also accept the legacy shape `{"seq":44}`.
- An upgrade that fails can't carry a readable body. On 401 or 404 during the
  upgrade, clients call `GET /changes` to learn the precise error code
  (`device_revoked`, `account_deleted`, …).
- The socket is only a hint. Clients must still pull on launch and foreground,
  and correctness never depends on the socket.

### 4.7 Health

**`GET /healthz`** (no `/v1` prefix) → `200 {"ok":true,"version":"<git sha or semver>"}`

### 4.8 Recovery key

A recovery key is a human-readable rendering of the 32-byte `rootKey`:
- **Encoding:** Crockford base32 (alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`), 52 characters.
- **Checksum:** 1 Crockford mod-37 check character appended, from the extended
  alphabet `*~$=U`.
- **Display:** groups of 4 separated by `-`.
- **Decoding** is case-insensitive, maps `I`/`L` → `1` and `O` → `0`, and
  ignores `-` and spaces. A checksum mismatch is rejected.
- `spec/vectors/crypto.json` pins an example. It's a client-only format; the
  server never sees it.

**Restoring** on a device that has nothing but the recovery key:
1. Decode the recovery key to `rootKey`, then derive the keys and the
   `accountId` (§2.1).
2. Send `POST /v1/devices` with a **fresh** device UUID (a revoked id can
   never register again, §4.2). That's the whole sign-in: there is no separate
   login call.
3. A `404 account_deleted` there means the account is gone (deleted or
   purged). The client may then create a new account with the same keys:
   `POST /accounts` with the derived `accountId` succeeds again once the old
   account no longer exists.

## 5. Server-side limits & lifecycle

| Item | Value |
|---|---|
| Record ciphertext | ≤ 65,536 bytes after decoding |
| Push request | ≤ 500 records and ≤ 4 MiB |
| Account | ≤ 10 MiB of live ciphertext and ≤ 100,000 live records |
| Tombstones | Purged 90 days after deletion. `compactedSeq` advances to the highest purged `seq`. |
| Inactivity | An account with no authenticated request for 365 days is deleted entirely. `lastSeen` is persisted at most once per UTC day. |
| Signup | A burst limit per IP plus a daily cap of 10 per IP (IPv6 grouped by /64) |
| Storage location | All account data lives in Durable Objects created with **EU jurisdiction** |

## 6. Client sync algorithm (informative, but the vectors assume it)

### 6.1 Per-record bookkeeping

For each record, a client keeps `{rid, logicalKey, version, lastSyncedPayload}`.
`lastSyncedPayload` is the base for 3-way merges.

### 6.2 One sync pass

1. **Pull.** `GET /changes?since=<stored nextSeq>` until `hasMore=false`. For
   each record:
   - decrypt it;
   - 3-way merge the base (`lastSyncedPayload`), the local value and the
     remote value with the collection's merge rules;
   - write the result locally;
   - store `version` and update `lastSyncedPayload` to the remote value.

   For a tombstone, delete it locally unless the local value has changed since
   the base. If it has, keep it and push it as a new version.

2. **Push.** Every local record whose value differs from `lastSyncedPayload`
   goes into a push with `baseVersion = version`.
   - `ok` → store the new version and the payload.
   - `conflict` → treat `current` as a pulled record (step 1), then retry the
     push. Give up after 3 rounds; the next pass picks it up.

### 6.3 Full resync

On `410`:
1. Pull with `since=0`.
2. Any local record whose `rid` isn't in the result is treated as deleted
   remotely, unless it changed locally.
3. Continue as normal.

### 6.4 Safety rules

- An empty or unreadable local store never pushes deletions. It resets its
  bookkeeping and pulls first.
- Device clocks never decide anything. `updatedAt` is only a tie-break inside
  merge rules.
